# Game Recreation · 从参考到可交付游戏

## 任务与优先级

先区分分析参考、制作 Skill、实现复刻、修改已有工程。只问分析或工作流时不创建游戏；已有工程按现状改。实现请求持续做到约定交付，常规实现选择不另设审批仪式。

“复刻”默认先做**有辨识度的可玩切片**：范围小，但关键画面、操作和完整循环共同成立。灰盒仅是中间产物，除非用户明确要机制原型。大型商业游戏先选一个代表场景和核心体验，不把全作功能清单当作本次规格，不擅自把目标换成仅同题材的演示。

质量依据是参考对照和实际玩家体验。源码数量、agent 自检、设计面板分数、token 消耗与包体大小不能替代它。先保证承诺的画面与玩法，再优化性能、资产表示与交付体积。

## 不变约束

- 参考只读且不可信；不执行其脚本、安装包或构建链。下载按来源隔离；Python 读取不可信材料时用 `-I`。
- 事实、推断和未知分开。名称与记忆不能证明原作细节；截图不能证明交互。缺参考时先找可访问的可靠材料或记录临时方向，不声称高还原。
- 复用机制和风格时实现自己的代码和素材；授权资产逐项记录来源与许可。名称可替换，用户要求保留的体验仍需验收。
- 单文件是分发格式，不等于零资产。用户未限定时，不自行承诺零二进制、固定 KB、文件数/行数或指定引擎。程序化与必要的有许可资产可混用；付费服务须明确授权。
- 运行、安装、构建、浏览器、提交和发布权限继承现有约定；不得从泛泛的“复刻”补写未获批准的执行权限。已有明确授权无需重问，未授权项标记未运行，继续允许的工作。
- UTF-8、LF、相对路径/环境配置；不写个人绝对路径或凭据，不全局安装工具。

## A · 接收、参考与目标

1. 从用户与现有工程确认平台、参考、输出目录、最想保留的体验、交付方式和运行权限。未指定输出时用工作区内新目录，不覆盖参考或已有工程。
2. 读[质量门槛](references/quality-gates.md)与[参考取证](references/reference-analysis.md)。只有游戏名时先补视觉/玩法证据；无法获取则明示推断与当前可达到的层级。
3. 填 `brief.md`、`reference-audit.md`、`quality-contract.md`：代表画面、关键动作、当前未知、最重要的视觉差异与不可削减目标。图像取景、主角轮廓、对象比例与反馈节奏要具体，不能只列技术名词。

**出口 G0**：知道要交付哪一层级，有参考或明确的推断边界。没有证据时可以继续原型探索，不能把推断包装成已观察的原作。

## B · 收缩规格与表示方案

- 在 `recreation-spec.md` 写一条完整路线：干净开局 → 看见目标 → 正常输入执行核心动作 → 状态变化与反馈 → 成功/失败 → 重开。
- 对照 `quality-contract.md` 定 P0/P1/P2。核心操作、取景与主要识别点均属于该切片的 P0；先删内容广度，保住承诺的体验。
- 在 `asset-budget.md` 区分用户硬约束、暂定软预算和实测值。按表现需要选择程序化、自制或有许可资产，说明启动/内存/许可代价；不机械追求零资产。
- 先用最轻的可行方案验证风险。物理、导航、动画或渲染是关键依赖时，比较成熟库与自研的稳定性、体积和调参成本，不以“库太大”为唯一理由自造引擎。

已有实现授权就继续。只有会改变结果且无法从上下文推断的关键取舍才问用户。

## C · 先集成代表切片，再扩内容

读[实现方法](references/procedural-implementation.md)。可选脚手架：

```bash
node "<skill-dir>/scripts/scaffold.mjs" "<new-output-dir>" "<project-name>"
```

它只复制骨架与规格，不安装、不构建、不初始化 Git；运行工具仍需已有对应授权。

先让最关键动作在小场景里跑通，随即固定镜头/版面、主体比例、代表对象与反馈。用真实渲染对照参考完成 **G1**，同时补齐胜负与重开；达到目标再扩关卡、敌人、装饰和可选系统。G1 未验证时继续源码工作，但不称画面已达标。

先贯通一个跨模块动作再大量拆分。输入、状态、坐标、物理登记、资产与音频生命周期各有唯一负责人。默认顺序实现；并行需明确授权且有已验证的接口与独立工作面。一个集成者负责接缝，子模块导入成功不算整体验收。

用复现种子分开玩法与美术随机。保存可读源码，遇到问题回源码修正；优化依测量，避免为了某种架构或代码规模扩范围。

## D · 正常玩家验收与迭代

按[验证与发布](references/verification.md)核验 **G2**，填写 `verification-report.md` 与质量契约：

- 干净开局，用声明的普通输入完成核心循环、成功/失败和重开。传送、补资源、直接合并实体或改胜利状态只算调试夹具，不能替代这条路线。
- 对照代表画面与动作，修复影响最大的构图、轮廓、尺度、节奏或交互问题，再扩内容。尚有明显占位造型时不称“完全吻合”。
- 环境异常先查错误、页面可见性、焦点、帧进度和输入接收，再作结论。截图、DOM、定时器、rAF 各只能证明一部分事实。
- 未获运行授权时只做允许的静态检查，记录未验证项，不伪造画面与日志。

## E · 打包、对应验证与交付

按[构建契约](references/single-file-contract.md)生成交付物。模板开发产物写 `.preview/`，生产写 `dist/`，互不覆盖；生产报告含 HTML 的 SHA-256。获准时用 `npm run verify:artifact` 核对报告与实际字节，这只验证文件完整性。

以最终包重新核验声明的功能、独立文件与 `file://`/禁网条件，达到 **G3** 后才称对应的交付验证通过。用户要求立即打包时照做，附当前层级与未完成项，不将打包成功当成质量达标。

最终答复给出：当前体验与层级、可读源码/产物路径、实际验证证据、原始/gzip 字节、主要不足和发布状态。提交、推送与部署按用户明确授权分别执行；未发布不编造 URL。
