# 实现方法：用规则表示资产，用模块组织行为

## 1. 技术栈按体验选择

| 体验需求 | 优先考虑 | 什么时候升级 |
| --- | --- | --- |
| 2D 拼图、消除、卡牌、轻量街机 | Canvas 2D + DOM UI | 绘制/粒子数量成为测量瓶颈 |
| 2D 复杂批量精灵、光效 | WebGL 或轻量 2D 渲染库 | 只引入实际需要的模块 |
| 3D 空间、光照、镜头与网格 | Three.js + 小型游戏逻辑层 | 复杂物理/导航确有需求才加库 |
| 已有成熟源码工程 | 保留框架与构建器 | 不为单文件目标先整体重写 |

单文件是交付形式，不是源码组织方式。物理、AI、后处理和帧率优化按需求加入，不把“复杂”当成质量。

核心玩法依赖碰撞、关节、导航或复杂动画时，先比较成熟库与自研方案的稳定性、交互表现、调参和维护成本。自研适用于可解释的受限规则；不要仅为压低包体，在尚未可玩的切片里同时制造物理、动画和建造框架。

## 2. 表示方法与代价

| 内容 | 低体积表示 | 要付出的成本 |
| --- | --- | --- |
| 重复环境/道具 | 参数化几何、种子布局、共享材质 | 造型受限，首次生成花时间 |
| 表面细节 | 小噪声场、Canvas 绘制、shader 程序纹理 | 需要控制频率/接缝，运行时显存仍占空间 |
| 法线/粗糙度 | 高度函数导数、离线或启动时烘焙 | 生成/采样成本，算法须与坐标空间一致 |
| 音效/环境音 | 噪声、振荡器、包络、滤波、卷积 | 设计时间，真实人声/音乐未必适合 |
| 动作 | 分层 transform、状态插值、程序化步态 | 复杂角色动作可能需要专用资源 |
| 字体/UI | 系统字体、DOM/CSS、简单矢量 | 跨平台字形/度量不同，需回退 |
| 必须的复杂素材 | 有许可的资源、合理分辨率/编码 | 预算与来源记录，不能叫零资产 |

base64 内联会增加编码体积；共享几何减少 draw call/内存，并不自动减少 bundler 产物中的任意数据数组。先确定表示方法，再看实例化优化。

按画面贡献分配资产预算：重复背景适合程序化；主角/棋子/核心道具、关键动作与代表地形应先满足 `quality-contract.md` 的轮廓、比例和层次要求。程序化结果不达标时可换手绘、自制模型或有许可的本地资源。精简的美术方向需要一致的造型与构图，不能用“低多边形”解释没有完成的占位模型。付费生成与第三方资产使用分别遵循授权和许可。

## 3. 小切片的顺序

1. 在一个小场景中用简单形状贯通最关键的输入、动作、碰撞/规则与反馈，尽早暴露跨模块风险。
2. 固定镜头或版面、主体占屏比例、移动方向和主要动作节奏；验证操作对象与交互目标同处可见、可触发范围。
3. 完成代表对象与环境的实际表现，对照参考修构图、轮廓、光色、层次与 UI。通过[质量门槛 G1](quality-gates.md)后再扩内容。
4. 在同一切片接齐成功、失败、重开、音频解锁与暂停，以普通输入完成 G2；画面与玩法交替修正。
5. 再扩关卡、角色变体、装饰与可选系统，每次扩展保留同一条回归路线。

灰盒是验证工具，不是默认成品；好看的开场也不能替代完整循环。没有运行权限时记录 G1/G2 未验证，不宣称完成。范围与模块数量依实际问题而定，不设代码行数、文件数或 agent 数配额。

## 4. 按复杂度拆模块

可选职责，而不是要求所有工程都建同样的目录：

- `core/`：时间、种子、配置、有限的事件接口。
- `game/`：状态、规则、目标、胜负与重开。
- `input/`：键鼠/触屏/手柄到统一动作，不让 UI 和逻辑同时抢输入。
- `world/`：布局与碰撞信息、程序化几何和纹理。
- `render/`：镜头、灯光、材质、可选后处理与质量档位。
- `audio/`：初始化、合成、事件响应、停止/淡出。
- `ui/`：状态投影与必要交互，不反向主导玩法状态。

高频可见对象直接遍历更新；跨系统事件只放在语义边界，例如开始、受伤、得分、结算。池化、合批与 DOM 缓存仅在相关场景使用。

### 集成契约与并行边界

先实现一次跨模块动作，再冻结必要的接口；契约应从可运行链路中提炼，不能凭空规定整套系统后同时填文件。默认顺序推进，已获并行授权也先判断工作面能否独立。

在 `recreation-spec.md` 记录唯一负责人及关键约定：

| 接缝 | 必须明确的事实 | 最小验证 |
| --- | --- | --- |
| 输入与 UI | 动作沿/保持的消费时机，菜单与游戏谁接收事件 | 开始、暂停、恢复、重开后仍能操作 |
| 相机与坐标 | 朝向、局部/世界坐标、单位、锚点/原点、画面/碰撞比例 | 向前输入与取景一致，核心目标可见且可触发 |
| 实体与资产 | 谁登记实体、谁同步位姿、谁释放资源；工厂返回 Mesh/Group/数据等具体类型 | 创建→移动→组合/销毁→重开，表示类型匹配，不重复登记或漏清 |
| 时间与物理 | 连续力/速度/能耗按帧还是固定子步更新，何时清累积器 | 改变每帧子步数后，相同时长的位移与资源消耗仍一致 |
| 状态与反馈 | 谁判定结算、谁播放音效/演出、事件载荷 | 单次动作只结算/反馈一次，重开仍有效 |

3D 拾取/建造还需验证：射线从哪里出发、持物沿指针还是镜头中心移动、可抓范围与可放置范围是否覆盖、吸附容差能否用普通操作达到；角色、载具、搭建物是否共享需要的支撑面。2D 网格则检查屏幕坐标到格子的映射、缩放与点击区域；各按实际类型取用。

在扩关卡前做跨系统可行性核算：所需资源数量与获取顺序、搬运/组合能力、承载或规则成本、路线距离/高度、速度与续航应共同支持目标。只生成某个物体、只画出某片地形、只设置终点触发器都不证明路线成立。最终结算的前置条件应对应承诺的循环；仅到达终点的捷径不能用来证明中途机制通过。

集成者负责契约变化与接缝回归，避免消费者一面猜接口一面写多重兜底。子模块导入、桩环境和独立仿真通过，只说明相应局部证据，不代表真实场景或正常路线通过。

## 5. 确定性与生命周期

- 复现种子、生成版本、分开的随机流。美术更改不应打乱玩法布局。
- 明确状态，例如 boot/menu/playing/paused/won/lost，进入/退出都定义清理。
- 失焦或解锁鼠标时释放按键；暂停不累积超大 dt。碰撞需要固定步进或 substep 时，不只靠 dt 钳制掩盖穿透。
- 音频须由用户手势创建/resume；失败不应使整个游戏崩溃；重开不要叠加环境音。
- 重开清掉计时器、实体、残留输入和 UI，再按种子重置；GPU 对象的释放与缓存复用要有清晰归属。
- 更新 GPU 变换/法线前确认坐标空间。Three.js `onBeforeCompile` 注入应匹配锁定版本的 shader chunk 顺序，不能使用尚未声明的变量。

## 6. 预算管理

不要先承诺固定 MB 或 fps。根据目标设备和参考复杂度，填 `asset-budget.md`：

- HTML 原始字节是本地文件体积；gzip/Brotli 是传输体积，服务端必须实际启用压缩才生效。
- 磁盘体积、启动时间、CPU 堆、纹理/几何显存分别看。一个 4K RGBA8 纹理基础层约 64 MiB，含 mipmap 还会增加。
- 生成任务可以分帧或缓存；遇到首启卡顿先找最长生成阶段，不单纯加假进度条。
- 画质调节基于前台实测采样；记录档位，不把降低像素数后获得的帧率当成原生分辨率表现。
- 超预算时先删低辨识度资源/效果、合并重复表示，再进行压缩；保留规则与源码可读性。
