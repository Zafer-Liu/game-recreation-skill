# 参考取证：把“看起来像”变成可实现的条件

## 1. 输入决定能证明什么

| 输入 | 可以观察 | 不能仅凭它确认 |
| --- | --- | --- |
| 本地 HTML/源码 | 静态依赖、资源表示、候选模块与算法 | 实际帧率、可玩性、网络行为、最终作者 |
| 可玩网页 | 操作、状态、反馈、完成/失败路径 | 服务端逻辑、完整素材许可、制作过程 |
| 录屏 | 可见时段的镜头、节奏、反馈、场景 | 未出现的操作、关卡、AI 规则 |
| 截图 | 构图、配色、比例、明暗、材质识别点 | 动画、音频、输入、碰撞、帧率 |
| 文字描述 | 用户期望 | 原游戏实际具备这些内容 |

用户只给截图时，先完成画面规格与可玩切片假设；把机制写成“本次实现选择”，不要称为原作机制。

### 只有游戏名称时

名称是检索入口，不是已经取到的参考。可访问时，优先读取官方玩法介绍、正常游玩截图和操作片段；区分游戏运行画面、宣传概念图与二次创作。记录出处、具体场景和可见事实，不能只写“公共知识”。浏览/联网权限不足时，说明参考缺口，可以先做临时方向或机制原型；依赖精确视觉才能决定的部分再向用户索取材料。

从材料选出代表画面与关键动作，填入 `quality-contract.md`。如果没有可观察材料，G0 的参考缺口应保持可见，不用想象补出精确还原数值。配色相似、同类型机制、原创替换命名分别是不同事实，都不足以单独证明复刻目标已达到。

## 2. 最小体验路径

在得到相应运行授权后：

1. 启动：进入方式、加载、首次操作、音频解锁。
2. 核心行动：移动/选取/跳跃/射击/消除等用户真正反复做的事情。
3. 状态变化：得分、资源、敌人、目标、失败压力。
4. 反馈：动画、音效、镜头、UI 是否及时且相互一致。
5. 结算：胜负条件能否达到，重开是否回到干净状态。
6. 边界：失焦、尺寸变化、暂停、输入释放。

不要为了“验证”执行未知安装程序或安装参考工程依赖。浏览器工具可用则优先用隔离浏览器；需要服务时只服务隔离副本，不暴露整个下载目录。

## 3. 视觉指纹

按贡献度挑 3–5 个识别点，写成可对照的描述：

- 镜头：俯视/侧视/第一人称、地平线位置、视野、速度。
- 形体：角色/道具轮廓、尺度关系、空间密度、负空间。
- 光色：主光方向、冷暖比例、亮度层次、雾对远景的遮蔽。
- 表面：粗糙度、边缘磨损、纹理频率、装饰密度。
- 时间：动作提前量、接触帧、余振、停顿、转场时长。
- 界面：信息位置、字号比例、危险色、反馈层级。

“有雾/有 Bloom/有阴影”不是画面规格。要说明它如何影响玩家看到的目标与层次。

## 4. 本地 HTML 取证

可选只读工具：`../scripts/inspect-html.mjs`（相对本文件）。它在未执行参考的情况下统计字节并报告候选：

- 原始 UTF-8 字节、gzip 字节、SHA-256。
- 内联 script/style 的数量与文本字节估计。
- 静态资源属性、data URI、网络 API 与图形/音频 API 信号。

其局限必须保留：这是启发式静态扫描，正则会命中注释、字符串与嵌套示例，不能遍历动态拼接 URL，也不能判断 tree-shaking、实际网络请求、图片是否运行时生成。输出是待核查线索。

下一步按证据进入局部代码：

- 纹理：CanvasTexture/DataTexture 的数据从哪来？是否又加载外部图片？
- 几何：参数化几何、数组数据还是外部模型？实例化是节省 draw call，还是也复用磁盘表示？
- 音频：合成缓冲区、采样文件还是远程生成？有没有显式用户手势解锁？
- 构建：真实 manifest、sourcemap、bundler metadata 优先于 minify 风格猜测。
- 离线：`src` 没有外链不能证明没有 fetch/import/字体/worker。

## 5. 避免把线索当结论

- 某段代码出现 `TAA` 不等于最终渲染路径启用了 TAA。
- 内存里有 134 张 texture，不等于有 134 张作者设计的图片，也不等于每张都来自 Canvas。
- 几何体/三角面统计会受阴影、后处理、多次 render 与计数重置影响；必须记录计数含义。
- 低档分辨率不证明高档可以流畅；隐藏页面、录屏与软件渲染会影响采样。
- 注释里的 agent 名称、meta 标签与 minify 命名不能证明使用了哪一个模型、几轮制作或多 agent 工作流。
- 引擎/业务体积不能按“第一次出现游戏名”的行号估算；没有构建元信息时只报整体与可直接测量的区块。

把每条结论写进 `templates/specs/reference-audit.md`，保留证据位置和置信限制。
