# 质量目标与阶段门槛

本文件定义什么证据足以继续扩展或声称完成。构建成功、文件数量、代码行数、agent 数、token 消耗和压缩率都不衡量复刻质量。门槛由实现者自行核验，不是每一步都让用户审批；运行权限仍继承用户约定。

## 1. 先确定交付层级

| 层级 | 要交付什么 | 不能冒充什么 |
| --- | --- | --- |
| 机制原型 | 用简化表现验证指定动作与规则 | 有辨识度的复刻成品 |
| 辨识度切片 | 小范围中，关键画面、操作与核心循环共同成立 | 原作的完整内容规模 |
| 高还原复刻 | 在明确场景中逐项对照参考的画面、节奏与交互 | 凭游戏名推测出的同题材作品 |

一般“复刻某游戏”的请求以**辨识度切片**起步，而非默认为灰盒机制演示。用户明确要高还原时按其目标执行，范围优先收缩到一个代表性场景；只给名称又无法访问参考时，先收集可访问的可靠画面或提出临时视觉方向，并明示这是推断。不要把“知识里的玩法列表”当作已经分析过的原作。

在 `quality-contract.md` 写下：目标层级、参考、玩家最在意的体验、不可退化的画面特征、可删内容和当前证据。更换名称与原创素材不等于可以替换用户想要的视觉和玩法目标。

## 2. 用可观察的差异描述画面

从实际参考选代表性的正常游玩画面，覆盖主体、环境与核心动作；记录出处和尺寸。为每个观察写“目标 → 当前差异 → 修正 → 对照证据”。关注：

- 构图与尺度：主体占屏比例、地平线/棋盘/舞台边界、近中远层次、目标在屏幕里的位置。
- 轮廓与动作：主角或操作对象的可辨轮廓、姿态变化、接触帧和关键动作弧线。
- 形体与材质：环境不是随机几何的堆积；重复元素有尺度和疏密，材质的色块/纹理频率服务于辨识。
- 光色与信息：亮暗区域、冷暖分布、交互高亮、危险反馈、UI 遮挡和文字可读性。
- 动态节奏：镜头、移动、等待、出手与回馈之间的时长关系。静态图不能证明节奏吻合。

具体目标来自参考与平台，不统一规定多边形数、色阶、引擎、粒子数量或后处理。截图不足以确定动作时，把待体验的动作列出来，不虚构精确数值。

## 3. 四道门槛

状态为 **通过 / 失败 / 未验证 / 不适用**；每个“通过”都指向同一版本的证据。“未验证”可以继续写源码，不能提升为已验证成品。

| 门槛 | 要看见的结果 | 未达到时怎么做 |
| --- | --- | --- |
| G0 目标可信 | 参考来源或推断边界明确；交付层级和关键差异已写清；平台与资产限制可行 | 补参考或缩小可声称的范围；继续可逆探索，不假装有高还原依据 |
| G1 代表场景成立 | 一个真实渲染场景中，主体、取景、尺度、光色达到契约；最关键输入与反馈可操作 | 修镜头、造型、资产与手感，暂缓扩地图、敌人和装饰系统 |
| G2 正常路线成立 | 从干净开局以声明的键鼠/触屏/手柄完成核心循环，达成成功与失败，重开后能再次开始 | 优先修可达性、交互发现、反馈和状态接缝；调试绕过单独归类 |
| G3 交付对应成立 | 被验收版本与最终包对应；独立文件、许可、生产模式和需要的离线条件有相应证据 | 标明已打包但未验证；不能用开发页的局部成功代替生产包验收 |

G1 与灰盒核心循环可以交替迭代：先证明动作能做，再把一个代表场景做到目标水准，随后扩展。不要先生成整套系统，最后才第一次看真实画面；也不要只做一张好看的开场图而不打通 G2。

运行被限制时，写清当前门槛未验证。用户要求“现在直接打包”时照做并标注当前层级、失败与未验证项，不以门槛为由阻拦已授权打包，也不补写通过记录。

## 4. 质量预算优先分给识别点

用户没有限定体积、零资产或技术栈时，不自行添加这些硬约束。先分配实现与迭代精力给主角/核心对象、相机/版面、主要动作与必要关卡，余量再给内容数量、背景细节和可选系统。

程序化、手工绘制、自制模型、有许可的本地资源可以混用。代表对象的程序化结果持续不达标时，更换表示方法；付费生成服务仍需明确授权。资源变大时记录收益与代价，压缩不能以丢掉主要识别点为代价。

复杂参考的删减规则是**删广度、保目标**：减少场景/关卡/敌人变体，保住承诺的操作和画面。用户的某项核心体验确实无法在现有约束下实现时，说明具体冲突再决定取舍。

## 5. 迭代应改变玩家看到或做到的事

每轮先挑对体验影响最大的差异，修改后用相同条件重看或重玩，并记录是否改善。连续修改仍未解决时重新检查表示方法、架构或范围，不无限加特效、调参数和堆规则。

可以保留灰盒作对照；灰盒、调试场景与成品截图分别标注。验收表中的形容词要换成可检查现象，例如“目标清楚”写成“普通操作路径中目标标记可见、交互提示在可触发位置出现”。数值是验收条件，不是凭空评出的还原度百分比。

## 6. 归因边界

失败复盘区分：执行者没有遵循已有规则、规则缺失/冲突、工具或环境故障、约束下的能力不足。一次任务无法比较模型强弱，不为模型或 skill 分配臆测的责任百分比。

若未来比较模型或提示词，固定同一参考、交付层级、运行授权、资源与预算，在不同游戏类型上对最终产物独立评价。先记录质量，再比较消耗；不以自评面板分数、代码量或更长思考推断结果更好。
